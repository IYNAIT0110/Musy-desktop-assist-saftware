# STARRA · 闪星：设计师端完整工作流 v1.0

> **文档性质：现有工作流与产品设计构想并列。** 已实现能力见新增的 v0.3.0 实际流程； 本文中的项目、人物、文件路径、界面、任务、数字与状态均为示例；Workspace、Graph、Timeline、Agents、Sync、Pack 的完整工作流及分阶段规划是目标体验，不代表当前版本已实现。具体可用功能以 [README](../README.md) 和 [使用指南](使用指南.md) 为准。

我建议把 STArra 设计成一种 以项目为中心、以文件关系为基础、以 AI Agent 为扩展能力的设计工作空间。

它不应该要求设计师放弃 Rhino、Grasshopper、SketchUp、Photoshop、D5 Render 等熟悉的软件，也不需要让所有设计工作发生在 STArra 内部。

STArra 的核心价值，是让设计师无论使用什么工具、在哪台电脑上工作、与哪个 Agent 协作，都能继续同一个项目，而不必反复寻找文件、理解旧版本和重建上下文。

下面用一个完整的建筑设计项目模拟设计师的使用过程。

## v0.3.0 实际可用流程


STArra v0.3.0 的实际可用流程：创建项目 → 收集资料 → 整理与记录 → 预览和复用 → 胶囊备份 → 换电脑继续。

## 1. 建立工作上下文

在织梦台创建项目，关联实际项目文件夹；顶部项目胶囊选择当前项目，按需要开启自动关联。

## 2. 收集与组织

在传送门收藏网页，在卷轴整理母子提示词，在百宝匣导入参考文件或剪贴板图片。通过小球快捷保存的新资料可默认关联当前项目；已有资料手动关联。

## 3. 记录与创作

用星砂的普通文本保存设计记录，待办事项列出行动项。需要时配置模型并使用 AI 优化，先核对再应用。Rhino、CAD、Photoshop 等仍在各自软件中使用，STArra 不替代原生编辑器。

## 4. 找回并复用

在织梦台按项目、类型、标签、关键词定位资料；百宝匣轻预览、并排参考，拖出原件。项目关联只记录关系，不移动源文件。

## 5. 用胶囊保存工作

离开当前电脑前，打开「胶囊」。做灾难恢复备份时选择完整备份；只想带走最近原件时选最近修改，或指定项目并叠加日期范围。

核对项目目录、引用原件、数据路径和附加资料库，决定是否包含密钥，扫描清单后处理缺失提示。选择源目录以外、最好另一块磁盘的保存位置，生成 .starrapack 文件夹。

范围只筛原文件；完整应用记录和当前资料库自有文件始终包含。因此胶囊适合个人备份迁移，不是可以直接发给客户的脱敏交付包。

## 6. 换电脑继续

在新电脑安装 STArra，复制整个备份文件夹，从胶囊执行恢复，选择新的工作目录。校验与复制成功后自动重启，并重建已打包路径。当前旧配置保留，外部软件与授权另行安装。

## 7. 定期检查

确认原件磁盘仍可访问，给重要阶段做独立备份。回收区的自有图片可能在 30 天后被清理，不应把回收区当归档。未选文件、缺失原件和断开的资料库需另外处理。

## 当前边界

mini 栏星笺、星轨、星镜仅 UI，点睛笔仍是占位。云同步、自动版本时间线、跨软件依赖追踪、自动 Agent 接力和脱敏交付包属于未来方向，不代表本版已实现。

以下继续保留长期目标体验，用于说明后续设计方向，不能将其中的未来功能当作当前能力。

| --- | --- |

## 一、从开始到交付的全流程

1. **建立项目 · STArra Workspace**：选择项目位置、创建项目结构、定义团队成员和工作阶段。
2. **收集资料 · STArra Workspace + Graph**：导入基地资料、参考图片、设计任务书，建立统一索引。
3. **方案探索 · STArra Graph + Timeline**：在原生设计软件中创作，记录关键文件、方案版本及其关系。
4. **设计深化 · STArra Agents**：调用不同 AI 工具完成分析、建模辅助、渲染等任务，并把产出关联回项目。
5. **评审修改 · STArra Timeline**：将会议意见、设计决策、修改任务和对应的文件版本关联起来。
6. **跨设备继续 · STArra Sync**：在另一台电脑恢复项目文件、索引和工作上下文。
7. **Agent 接力 · STArra Agents + Pack**：导出任务交接说明及文件引用，让另一个 Agent 在既有成果上继续。
8. **交付归档 · STArra Pack**：整理最终文件、依赖、版本和决策记录，生成可复用的项目包。

这一流程中，设计师实际会经历三个状态：创建项目、持续创作、交付与复用。STArra 的各项功能贯穿其中，而不是成为设计师必须反复打开的多个独立软件。

## 二、设计师实际怎么操作 STArra？

### 阶段 1：创建项目

STArra Workspace · 项目工作台

设计师第一次打开 STArra，看到的应该是自己的项目列表，而不是一个复杂的文件管理器。

**界面概念（假想状态）**

```text
starra / workspace
你的项目：河岸社区艺术中心 · 方案设计 · 进行中
创建新项目：从模板或空白项目开始
当前项目位置：D:\Projects\Riverside-Art-Center
本地项目目录已关联
```

设计师操作：

1. 点击「创建项目」，填写项目名称、类型、设计阶段及本地文件路径。
2. 选择「建筑设计项目」模板，自动建立约定的目录和项目标识。
3. 导入原有资料，或者从空项目开始。
4. 选择是否启用同步和 AI Agent 功能。

STArra 根据项目模板创建建议目录：

```
Riverside-Art-Center/
├── 00_Brief/           任务书与基础资料
├── 01_Research/        场地分析、案例研究
├── 02_Concept/         概念方案
├── 03_Design/          模型、图纸与设计文件
├── 04_Visualization/   渲染、图片与视频
├── 05_Review/          评审与修改意见
├── 06_Deliverables/    正式交付成果
└── .starra/            项目索引及配置
```

这里有一个重要的设计原则：用户不应该被强制使用固定的目录结构。

有些工作室已经有自己的文件管理规范。STArra 应允许保留原有目录，通过索引建立项目关联，而不是要求设计师搬动大量文件。

### 阶段 2：收集与组织设计资料

STArra Graph · 项目星图

设计师将任务书、现场照片、测绘图、参考案例和设计规范拖入项目。

STArra 需要完成两项工作：

第一层：统一索引。 记录文件的位置、格式、修改时间、所属项目和唯一 ID。

第二层：建立关联。 让文件不只是目录中的独立对象，而是设计过程中的可追踪节点。

**项目关联示意。** 实际关系图应该按关联类型、文件数量和设计阶段筛选，而不是一次展示所有文件。

例如，设计师创建 `Concept_A.3dm`，可以将它关联到：

- 作为设计依据的任务书和基地条件。
- 参考的案例与草图。
- 由它导出的效果图。
- 后续产生的修改版本。

这里我不建议 STArra 完全依赖 AI 自动判断关联。

更可靠的方式是：软件原生插件和文件事件提供明确关联，用户手动补充设计语义，AI 只负责建议尚未确认的关系。

这样可以避免 AI 把两个仅仅名称相似的文件错误地认定为上下游依赖。

### 阶段 3：开始设计与版本迭代

STArra Timeline · 创作时间线

设计师在 Rhino 中建立第一版体量模型。

保存文件之后，STArra 在合适的时机记录文件变化，但不应该每次保存都生成一个重要的设计版本。

我建议区分：

- 自动文件快照：供恢复和技术比较使用。
- 设计里程碑：由设计师确认，记录阶段性成果和修改原因。

**Concept_A · Timeline 版本历史示例**

| 里程碑 | 时间 | 设计说明 |
| --- | --- | --- |
| V1 · 初始体量 | 第 1 周 | 根据功能需求建立初步体量关系。 |
| V2 · 优化建筑朝向 | 第 2 周 | 根据日照分析调整建筑主入口与整体朝向。 |
| V3 · 调整中庭尺度 | 第 3 周 | 根据评审意见扩大中庭、调整功能动线。 |

设计师可以点击任意里程碑，查看：

版本对应的模型文件、效果图、参考资料、修改说明、决策来源，以及与前后版本的关系。

以后想知道「为什么二楼的悬挑被取消了」，不必翻找几个月前的微信群消息。

但需要注意，文件版本管理不等于能够自动识别 Rhino 几何模型发生了什么变化。几何差异对比需要独立的 Rhino 集成能力，不能仅依靠普通文件索引实现。

### 阶段 4：使用多个 AI Agent 协作

STArra Agents · 智能体协作

这是我认为 STArra 最有潜力形成差异化的功能之一。

假设设计师需要根据 Rhino 模型生成建筑效果图，并对比多个设计方案。

工作过程如下：

**Agent 协作流程示例**

1. 建筑师创建任务：「生成两套立面材料方案，保留现有体量」。
2. Agent A 执行模型检查与分析，Agent B 生成效果图。
3. 产出文件、来源、任务记录和关联关系写入同一 STArra 项目。
4. 设计师审核并选定方案，保留决策，进入下一轮设计。

设计师不需要亲自把每份 AI 产出重新分类，但 STArra 必须能够知道：

哪个 Agent 执行了什么任务、使用了哪个版本的输入文件、生成了哪些结果、结果是否经过设计师确认。

这里还要建立清楚的权限边界：Agent 默认不允许覆盖正式成果，任何会修改原始设计文件的操作都应有明确授权和恢复机制。

### 阶段 5：设计评审与修改意见

STArra Timeline + Graph · 决策与文件关联

到了第三周，设计师参加项目评审会议。

甲方提出：「主入口需要更明显，中庭应该扩大，还要减少西侧玻璃幕墙面积。」

传统工作方式下，这些意见可能散落在录音、微信消息、会议纪要和待办清单里。

在 STArra 中，理想的操作是：

1. 将会议录音、文字纪要或手动记录导入项目。
2. AI 提取可能的修改事项，由设计师审核确认。
3. 将每条意见与对应的模型、图纸、效果图以及当前版本关联。
4. 设计师打开 Rhino 修改模型，完成后标记事项并关联新版本。
5. STArra 保留从「原始意见」到「修改成果」的可追溯路径。

**Review · 第三轮设计评审（示例，3 条事项）**

| 事项 | 关联文件 | 状态 |
| --- | --- | --- |
| 扩大中庭面积 | `Concept_V3.3dm` | 已完成 |
| 调整主入口标识 | `Entrance_View.png` | 待修改 |
| 优化西侧幕墙 | `Facade_Study.3dm` | 待修改 |

交互示意：可勾选评审事项。仅用于展示预期操作，不会写入真实项目。

这里的核心不只是自动生成待办事项，而是让每条修改意见真正关联到设计成果。

### 阶段 6：跨设备继续工作

STArra Sync · 跨设备同步

设计师白天在办公室台式机上使用 Rhino，晚上想在家里的电脑上继续设计。

理想工作流如下：

- 办公室电脑：`D:\Work\Project_A`。
- 家用电脑：`E:\Design\Project_A`。
- 同步文件与项目索引，转换本地路径映射，恢复项目上下文。

文件关系、版本、任务记录和决策信息在另一台电脑上仍然可用。

关键是 STArra 不应使用 `D:\Work\...` 这样的绝对路径作为文件的唯一身份。它需要稳定的文件 ID、项目相对路径以及不同设备的路径映射。

此外，索引同步和实际文件内容同步是两回事。文件本体可以通过 STArra 的存储服务或用户选择的第三方云盘传输，但必须明确哪些文件已经下载、哪些文件还只存在于远端。

对于 Rhino、Revit 等设计文件，还需要考虑文件占用、多人修改冲突和依赖资源路径。不能简单承诺「所有软件都能无缝同步」。

### 阶段 7：Agent 中断后的任务接力

STArra Agents + Pack · 任务接力

这是你此前提出过的一个非常具体的需求：

当 Agent A 积分用完、服务中断，或者用户想换用 Agent B 时，不希望重新描述项目、重新上传所有文件。

我建议 STArra 增加一个明确的动作：

「生成交接包」 (Create Handoff)

交接包可以采用可读的 Markdown 文件，以及一个结构化的 JSON 清单。

**Agent Handoff · `handoff.md` 示例**

```markdown
# 河岸社区艺术中心 · Agent 交接
- 当前任务：优化立面材料方案
- 已完成：方案 A 效果图生成
- 未完成：方案 B 及对比报告
- 输入文件：Concept_V3.3dm
- 已有成果：Facade_A.png
- 限制条件：保留现有体量
- 下一步：生成方案 B 并比较优缺点
```

Agent B 读取交接信息，识别已完成工作、现有文件和下一步任务，在获得授权后继续执行。

这项功能真正有价值的地方在于：用户不必完全依赖某一个 AI 平台的对话历史。

但需要说明：不同 Agent 的工具权限、模型能力和文件格式支持并不相同。交接包能够传递上下文，不保证另一个 Agent 可以无损接管所有任务。这是 STArra 需要通过适配器和任务验证机制逐步解决的问题。

### 阶段 8：正式交付与项目归档

STArra Pack · 项目打包与归档

项目结束时，设计师选择「生成交付包」。

STArra 应提供两种打包模式：

| 模式 | 内容与用途 |
| --- | --- |
| 正式交付包 · Delivery Pack | 只包含经过确认的图纸、模型、图片、报告以及必需的外部依赖。适合交付甲方、顾问或合作方，不暴露不必要的内部讨论和 Agent 历史。 |
| 项目归档包 · Archive Pack | 在权限允许的范围内，保存阶段版本、文件关联、设计决策、任务记录、相关文件及项目配置。适合团队内部长期存档或跨设备迁移。 |

交付完成后，设计师仍可以通过 STArra 查看一个设计决策为何发生、最终采用了哪个方案以及该成果依赖哪些文件。

这使得项目不仅留下成果，还留下可复用的设计知识。

## 三、设计师每天打开 STArra 时应该看到什么？

前面是完整项目周期。真正决定 STArra 有没有人愿意每天使用的，是它的日常体验。

我建议将首页设计为 Project Home（项目主页），重点不在展示文件数量，而在让设计师马上知道：

今天应该做什么？上次做到哪里？哪些文件发生了变化？哪个 Agent 需要我的确认？

### Project Home · 河岸社区艺术中心（概念 UI）

```text
starra / Project Home
河岸社区艺术中心 · 方案深化 · 第 4 周 · 进行中
继续上次的工作：Concept_V3.3dm（中庭尺度调整）
待处理：3 条评审修改事项
Agent：1 个结果待审核
最近的项目活动：Concept_V3.3dm 已更新；立面材料方案 A 已生成；新增 3 条评审意见
导航：Workspace / Graph / Timeline / Agents / Sync / Pack
```

所有文件名称、数字及状态均为示例数据。

理想情况下，设计师一天的 STArra 操作可能只有：

早晨打开项目主页，查看待处理事项；点击上次的 Rhino 文件继续设计；完成一个重要版本时保存里程碑；将渲染任务交给 Agent；下午审阅 Agent 产出；晚上在另一台电脑继续。

STArra 不应该让设计师每天花很多时间整理 STArra 本身。 大部分文件索引、关联收集和状态更新应在后台自动完成，只有涉及设计意图、重要版本和决策时才需要人工确认。

## 四、六个核心功能如何形成完整系统？

| 产品功能      | 主要职责              | 用户获得的价值   |
| --------- | ----------------- | --------- |
| Workspace | 项目主页、文件入口、任务与工作状态 | 快速回到工作    |
| Graph     | 文件统一索引、依赖和关系      | 找到文件及上下游  |
| Timeline  | 版本、事件、决策记录        | 理解项目演变    |
| Agents    | 外部 AI 接入、任务执行和交接  | 减少重复说明与操作 |
| Sync      | 多设备同步、路径映射        | 换设备继续工作   |
| Pack      | 文件依赖检查、交付与迁移      | 完整交接和归档   |

这里有一个架构上很重要的区别：

Graph 应该是整个系统的底层能力，而不是只供用户打开的关系图页面。

例如 Timeline 记录的版本、Agents 生成的文件、Pack 打包的依赖，都需要使用同一套项目身份与文件关系数据。否则六个功能就会变成六个互不相通的模块，这恰好违背 STArra 的初衷。

## 五、我建议的实际开发顺序

虽然上面的流程完整，但不建议一次性开发全部功能。

### MVP：Workspace + Graph + 基础 Timeline

优先实现项目创建、已有文件导入、文件索引、手动或规则关联、关键版本记录和基本搜索。

这是最先需要验证的价值：设计师是否真的能更快找到文件、恢复项目上下文。

### 第二阶段：Pack + 基础 Agents

先把项目元数据打包、Markdown 交接和指定目录的 Agent 产出导入做好，而不是直接兼容所有 AI 产品。

验证 Agent 接力能否降低重复操作成本。

### 第三阶段：Sync + 深度软件集成

加入稳定的文件同步、冲突处理、Rhino/Grasshopper 等工具插件，以及更自动化的文件关系识别。

这是工程成本较高的阶段，需要在前两阶段验证需求后推进。

## 六、用一个实际问题检验 STArra 是否有价值

假设三个月后，甲方说：

> 我们想回到第二版方案，但保留第四版的材料设计，同时让另一个 AI Agent 帮我们重新生成效果图。

在没有 STArra 的情况下，设计师需要寻找旧 Rhino 文件、确认不同版本的效果图、回忆对应材料、整理依赖文件，再向 Agent 重新解释背景。

在理想的 STArra 工作流中，设计师可以：

1. 在 Timeline 中找到第二版体量方案。
2. 在 Graph 中定位第四版材料及其关联文件。
3. 在 Workspace 中创建新的方案分支，保留原始版本。
4. 通过 Agents 生成带有指定版本引用的任务交接包。
5. 检查新 Agent 的输出，确认后保存为新的设计里程碑。
6. 使用 Pack 导出新方案，或通过 Sync 交给另一台电脑上的协作者。

这个场景贯穿了 STArra 的所有核心价值：文件能找到、版本能解释、决策能追溯、工作能继续。

但它是目标体验，而不是现有系统已经具备的能力。尤其是跨版本组合模型和材料，可能需要依赖具体设计软件或人工处理，STArra 不能仅凭文件关系就自动完成。

## 七、最终产品判断

我认为 STArra 不应该做成三个东西：

- 另一个普通云盘：市场上已经有成熟的文件存储与同步产品。
- 另一个 Milanote：它的优势不应该停留在灵感收集和视觉白板。
- 另一个全能设计 Agent：让 STArra 自己承担所有绘图、建模、渲染工作，会大幅增加开发成本，也会削弱它的平台定位。

它应该成为位于现有设计软件和 AI Agent 之间的项目上下文层。

因此，我建议把 STArra 的用户工作流浓缩为：

### Organize → Connect → Create → Continue

组织项目 → 连接信息 → 自由创作 → 持续工作

这一定位和之前的品牌故事「让创造，自有星图」能够统一起来。

我认为 STArra 最值得追求的体验是：设计师感觉自己一直在使用熟悉的设计软件，但无论项目变得多复杂，都不再轻易失去设计过程的上下文。

这也是后续设计界面、确定功能优先级和验证 MVP 时，最应该坚持的原则。
