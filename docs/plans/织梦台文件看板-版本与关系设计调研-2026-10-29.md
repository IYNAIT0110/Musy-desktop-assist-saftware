# 织梦台文件看板：版本、日期与文件关系

日期：2026-10-29。当前基础：STArra v0.3.2。性质：产品设计与公开案例调研，保留原始方案；v0.3.3 已交付文件看板第一阶段，详见 [交付与后续优先级](织梦台文件看板-v0.3.3开发交付.md)。优先级调整：先解决文件看板，再推进项目概览、任务与成果页面的总体重排。

## 1. 设计目标

用户打开项目后，应能快速回答：

- 我需要的模型、图纸、图片或汇报文件在哪里？
- 哪个是最新修改，哪个是已经确认或交付的版本？
- 前几天做过什么，哪些文件在同一个工作节点发生变化？
- 这个 PDF、图片或模型来自哪一个源文件、哪一版？
- 当前文件引用了谁、被谁使用，改动后哪些关联内容需要核对？

建议以“文件族”为主入口，配合文件、时间、关系三种视图。它们共享同一份索引、版本记录和关系，不复制三套文件。磁盘目录作为位置维度保留，不要求用户重整原文件夹。

## 2. 先分清容易混淆的概念

| 概念 | 示例 | 建议规则 |
| --- | --- | --- |
| 文件类型 | 3DM、DWG、GH、SKP、PSD、PNG、PDF、PPTX | 类型用于筛选和预览，不直接决定文件之间的关系 |
| 同一文件的历史版本 | 模型.3dm 在三个时点保存的副本 | 同一条版本线，可展开并比较 |
| 平行方案 | 方案 A.3dm、方案 B.3dm | 是分支或备选方案，不强排为前后修改稿 |
| 派生文件 | 模型导出的 DWG，DWG 导出的 PDF | 各自有身份和版本，用“导出自”连接 |
| 技术依赖 | DWG 外部参照、模型贴图 | 有方向的“引用”关系，实际解析或用户确认后才成立 |
| 设计语义关系 | 一张参考图启发某个模型 | 人工注明“参考”，不宣称是软件依赖 |
| 重复副本 | 相同内容出现在两个目录 | 可标记内容一致；不因此把两份文件合并或删除 |

尤其不能把同名不同格式的文件自动塞进同一个版本堆。即使某些评审工具允许混合堆叠，STArra 也应优先保留“源文件—派生文件”的方向，帮助设计师追溯。

## 3. 默认文件视图

### 看板结构

上方：项目名称、搜索、文件 / 时间 / 关系切换。

筛选行：类型、修改日期、阶段、文件状态；默认只保留高频项，其余收进筛选菜单。

主区域：按文件族折叠的卡片，允许切换紧凑列表。默认按最近修改排序；也可按日期分组，或按模型、图纸、图像、文档等类别分组。阶段分组需要用户已定义阶段，不强制推断。

选中后：在详情中显示预览、版本、关联。窄悬浮窗采用覆盖式详情或四级详情窗，展开后保留原看板位置；宽窗口才并排显示详情，避免三个窄栏挤占预览。

### 文件族卡片

```text
┌──────────────────────────────┐
│           真实预览           │
│                        4 版本│
├──────────────────────────────┤
│ 庭院模型                 3DM │
│ 当前工作稿 v4 · 10/29 15:20   │
│ 引用 2 · 派生 3 · 待核对 1   │
└──────────────────────────────┘
```

- 单击选择并查看详情，双击外部打开，空格快速预览；在关系图中单击只聚焦，避免误打开。
- 版本数量有独立点击区域，展开历史条目，保持卡片位置稳定。
- “当前工作稿”“最近修改”“确认稿”“已交付”是不同状态。确认稿必须由用户标记；后续修改不能默默继承已交付状态。
- 缩略图不可用时显示类型、文件名和原因；模型截图只是预览，不等于几何内容的完整比较。
- 阶段、用途、版本归组等只调整看板元数据，默认不移动或重命名磁盘文件。

## 4. 时间视图：看清项目怎样演变

第一层按今天、昨天、具体日期汇总；每一天展示发生变化的文件族。展开文件后才显示当天捕获的版本或事件，避免每次自动保存形成一张卡。

示例：

```text
10/29  下午修改
  庭院模型 v4       入口调整
  平面图 v3         用户确认由模型 v4 导出
  汇报.pdf          来源为平面图 v2，待核对

10/27  第一轮汇报【项目节点】
  庭院模型 v2  /  平面图 v2  /  汇报.pdf v1
```

时间字段必须标明含义：

- 修改时间：磁盘报告的最后写入时间，用于最近修改排序。
- 首次发现：STArra 首次记录到文件的时间，不冒充创作时间。
- 保存快照时间：STArra 实际保存可恢复内容的时间。
- 文件名日期：候选描述，例如“1027”，不能作为真实系统时间使用。
- 项目节点时间：用户命名并保存的一组版本，例如“第一轮汇报”。

复制、同步、恢复都可能改变时间属性，因此修改时间不能单独证明版本先后。项目节点应记录一组具体版本；节点建立不代表这些文件在其他软件中已经互相匹配，未验证时明确说明。

## 5. 版本视图：折叠复杂度，保留选择

两种来源分别处理：

1. 磁盘上已经另存了多个文件：STArra 建议归组，用户确认后组成文件族，保留每个真实路径。通过名称、目录、类型等提出候选，不自动覆盖或删除。
2. 同一路径不断覆盖：只有实际保存了快照或接入有效版本后端，才能承诺恢复历史。记录“检测到修改”不等于保存了旧内容；无法补回接管前已被覆盖的历史。

用户可以拆分错误的版本组、把某一版设为当前工作版本、另建平行方案，也可以保留“确认稿”标记。版本顺序和分支应以明确记录为准，不能把文件名“最终版”当作事实。

比较能力分级：

- 先提供缩略图、时间、大小、说明与双栏预览。
- 图片可后续提供同步缩放与滑动叠加；不同尺寸须明确对齐规则。
- PDF 可提供页级对照，前提是接入页渲染和对应规则。
- Rhino、CAD、SU、GH 的语义差异比较属于专门适配，不宣称仅凭缩略图就知道哪些几何或参数发生变化。

默认“恢复为副本”，避免覆盖当前工作；恢复原位需要确认和恢复前保护。

## 6. 关系视图：先看局部，再逐步展开

### 已确认的图谱形式

2026-10-29，用户确认以所附 Obsidian 关系图截图作为视觉基准：圆点节点、细线连接、节点旁文字标签、疏朗的网络布局。关系图不采用文件缩略图卡片、矩形流程节点或卡片间的粗箭头；文件卡片仍属于文件看板，与此视图区分。

- 每个圆点代表一个文件或折叠的文件族，文字显示名称；版本组展开后可以查看具体版本，层级须明确。
- 默认使用克制的节点与细线颜色，沿用 STArra 当前配色和材质。节点尺寸可适度表达关联数量，当前选中状态单独强调，具体大小规则在原型中验证。
- 悬停或选中时突出节点、名称及直接关联线，其余适度淡化；支持缩放、平移、搜索定位与拖动节点。
- 默认不在全部连线上铺满关系文字和箭头。聚焦某条关系时再显示方向、关系名称、证据和对应版本，保持全图清晰。
- 首次显示优先围绕当前文件的局部网络，可按需扩展到全项目。文字避让、节点重叠与大量文件的聚合方式需在原型中验证。
- 截图确认的是视觉表达方式；自动识别、节点尺寸、布局参数等属于待验证设计，不能由外观推断已存在真实关系。

### 关系类型

| 关系 | 例子 | 证据来源 |
| --- | --- | --- |
| 前一版本 / 分支自 | 模型 v2 → 模型 v3 | 快照记录或用户确认 |
| 导出自 / 生成自 | 模型 v3 → 平面 DWG v2 | 用户确认、可信插件、明确操作事件 |
| 引用了 / 被引用 | DWG 引用底图；模型使用贴图 | 格式解析或设计软件插件；人工关系单独标明 |
| 参考 | 参考图 → 模型 | 用户手动标记，或模型建议经确认 |
| 属于项目节点 | 多个版本属于第一轮汇报 | 用户保存节点 |

源文件和派生文件之间，应尽量连接到具体版本。例如“汇报 PDF 来自平面图 v2”，而不是永远连接到会变化的“平面图最新版本”。

### 推荐交互

- 默认以选中文件为聚焦中心采用网络布局；上下游方向在聚焦连线或详情中明确，不强制排成左右流程图。
- 首屏只显示直接关联，点击“再展开一层”增加范围。大量贴图先折叠为“贴图 12 个”。
- 上方可切换“全部关系 / 来源与产出 / 技术依赖 / 版本演变”。
- 连线使用文字标签与线型，不单靠颜色。实线表示明确关系，虚线表示待确认候选；来源和时间可点开查看。
- 允许多选文件后“建立关系”，并选择类型。拖拽连接必须二次选择关系含义，不把拖近视作建立依赖。
- 图谱变动只影响元数据，不改磁盘文件。关系可编辑、删除、撤销。

### 影响提醒

模型 v3 更新为 v4，而某张图纸记录为基于 v3：提示“上游已有新版本，请核对”。不能直接断言图纸错误或过期，也不自动重生成。实际依赖丢失则另外显示“引用文件未找到”。

## 7. 案例与适用边界

### Frame.io：版本堆与对比

官方版本说明展示拖动创建版本堆、单缩略图收纳多个版本、展开历史与调整顺序。新版另区分 Version Saves，自动保存历史需要 Frame.io Drive 的 Mounted Storage。它适合借鉴版本入口与历史对比，但本地扫描并不会天然拥有这套云端历史能力。

- [Versioning in Frame.io](https://help.frame.io/en/articles/9101068-versioning-in-frame-io)
- [Comparison Viewer](https://help.frame.io/en/articles/9952618-comparison-viewer)

借鉴：卡片上的版本计数、历史侧栏、双栏和图片叠加对比。STArra 的派生文件仍单独关联，避免丢掉生成关系。

### Anchorpoint：创作文件的版本节点

官方文档将提交描述为冻结文件状态的项目检查点，单文件可看历史，并提供 Restore as Copy。

- [Settings and commands](https://docs.anchorpoint.app/git/settings-and-commands/)
- [Version history](https://docs.anchorpoint.app/git/versions/)

借鉴：项目节点、改动清单、恢复为副本。是否引入 Git/LFS 或自有快照存储应单独评估，先确定保留策略和大文件成本。

### Autodesk Vault：Uses / Where Used

官方 Inventor 集成说明区分当前文件使用了哪些文件、哪些文件引用了当前文件，还可查看历史版本的关系。相关页标明 Uses/Where Used 适用于对应的 Workgroup/Professional 版本；不能据此推断所有格式均能通用解析。

- [Show Details in Inventor](https://help.autodesk.com/cloudhelp/2022/ENU/Vault-General/files/GUID-6144B56D-516A-406F-8FDA-759650869815.htm)

借鉴：明确的关系方向、上下游入口、版本对应的关系。STArra 第一版以人工确认关系为主，不承诺跨 Rhino/CAD/SU/PS 的全自动依赖识别。

### Autodesk Docs：当前版本与版本历史

官方说明中，同目录同名同扩展名上传会创建新版本；用户可将旧版本设为当前，显示的版本号不必等于总版本数。

- [View Version History](https://help.autodesk.com/cloudhelp/ENU/Docs-Files/files/file-folder-actions/View_Version_History_Docs.html)

借鉴：“当前使用”和“最后生成”分开显示。STArra 本地目录中的同名文件不能直接照搬云上传识别规则。

### Obsidian Canvas / PureRef：空间表达

Obsidian Canvas 用文件、笔记与网页卡片构成空间关系，支持分组与连线；PureRef 则围绕参考图片的空间排布、对齐和随手查看。

- [Obsidian Canvas](https://obsidian.md/help/plugins/canvas)
- [PureRef](https://www.pureref.com/)

借鉴：以预览内容为主的卡片和分组。自由摆放可以是可选模式，日常默认采用稳定的自动排列，避免文件多后需要手工维护布局。画布上的连线只有被定义了含义和证据后，才是可用于影响提醒的文件关系。

### Eagle：视觉浏览与智能分类

官方整理说明覆盖标签、文件夹、智能文件夹与相同/相似文件扫描。

- [Organize](https://en.eagle.cool/support/desktop/organize)

借鉴：视觉预览、筛选与保存的分类规则。该页面没有提供设计文件版本谱系的依据，不能把素材分类等同于版本和依赖管理。

## 8. 可用开源基础

- [React Flow / xyflow](https://github.com/xyflow/xyflow)：MIT 许可的节点界面库，可构建关系画布；业务关系、版本身份和文件快照需要自己实现。官方许可说明见 [Open Source](https://xyflow.com/open-source)。
- [JSON Canvas](https://github.com/obsidianmd/jsoncanvas)：MIT 的开放画布格式和规范；[规范](https://jsoncanvas.org/spec/1.0/)定义文件/文本/链接/分组节点及带方向、标签的边。可参考导入导出与布局存储，但并不内置文件版本模型、历史恢复或关系证据。

开源的是以上库和格式；不能据此把 Obsidian 应用本体、Frame.io、Vault 或 Anchorpoint 的产品代码视为可复用源码。本轮不安装依赖或复制第三方实现。

## 9. 建议开发顺序

1. 文件看板底座：明确“项目目录扫描”与“已关联资料”的范围，目录索引、预览、类型/日期筛选、稳定文件身份、失效状态和增量刷新。选择项目目录与开始扫描应分开确认范围，排除临时目录、备份包、符号链接循环，不默认扫描全盘。
2. 现有文件版本归组：版本堆、手动确认/拆分、平行方案、历史展开，不改原文件。
3. 关系看板：人工标注来源/派生/参考，记录具体版本；局部关系图与上游更新待核对提示。先让关系可看、可改、可撤销。
4. 真正的版本保存与项目节点：可恢复快照、容量/保留策略、恢复为副本，再逐步增加自动保存。对持续写入中的大文件等待稳定并校验，失败不生成“备份成功”。多文件节点要报告捕获窗口与未完成项，不假装是设计软件原子保存。
5. 专业适配与智能辅助：已支持格式的引用解析、插件事件、名称候选建议与更细比较。AI 建议不静默创建真实依赖。

第一轮原型用同一示例项目验证三种视图：模型 v1/v2/v3、DWG、GH、贴图、渲染图、PSD、PDF/PPT。至少覆盖平行 A/B、源文件更新而导出未更新、文件改名/移动、失效链接、相同内容副本与不能预览的格式。

## 10. 对当前代码基础的判断

当前项目只保存 root 路径和网站/卷轴/素材关联，root 本身不代表已扫描完整项目目录。现有“继续工作”是打开/复制事件，不是磁盘变更历史或文件快照。现有缩略图与统一索引可复用，但要增加独立文件身份、版本组、版本记录与关系记录，才能支撑上述看板。

建议下一步先制作文件、版本展开、局部关系三个状态的低保真交互原型，再确定快照实现。先验证用户能否用两三次操作回答“这份汇报来自哪版模型”，比先增加装饰动画更有价值。
